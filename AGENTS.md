# This is NOT the Next.js you know

This version has breaking changes — APIs, conventions, and file structure may all differ from your training data. Read the relevant guide in `node_modules/next/dist/docs/` before writing any code. Heed deprecation notices.

## RetailAgentOS product principle (shared — keep in sync with CLAUDE.md)

Simplicity for retailers and executives is a product requirement. Lead with the business outcome before protocols, schemas or architecture. A retail executive should understand the value in two minutes. A retail SME or product manager should be able to prepare catalog and policy inputs without writing code. Technical implementation details should remain available, but progressively disclosed after the value and next action are clear.

## Agent-ready storefront and WebMCP platform

RetailAgentOS is expanding additively from a deterministic merchant-reasoning engine into a multi-channel agent-storefront platform. Before changing platform, WebMCP, connector, showcase, or merchant-onboarding code, read [`specs/WEBMCP-PLATFORM-BUILD.md`](./specs/WEBMCP-PLATFORM-BUILD.md), [`specs/reference-implementation/README.md`](./specs/reference-implementation/README.md), and relevant merchant reference documents.

- `@retailagentos/engine` remains the deterministic source of commerce decisions; browser, SaaS, connector, network, tenant, analytics, and authentication concerns stay outside it.
- UCP, MCP, WebMCP, feeds, Schema.org, and human UI derive from the same canonical merchant/catalog/policy objects. WebMCP results must not recalculate decisions.
- Owned storefronts may integrate WebMCP and cart preparation; marketplace integrations use connector and checkout-handoff mode.
- Label experimental WebMCP behavior honestly, degrade gracefully, and update the build document after every material phase with tests and the next safe action.
- The canonical Phase 1 route is `/webmcp-showcase`; `/agent-ready-storefront` is retained as a compatibility entry point. The page must call the WebMCP registration lifecycle, display actual registered-tool results, and abort registrations on unmount. Feature detection alone is not native-WebMCP proof.
- Keep controlled Fresh Corner and TheCustomHub-style fixtures separate from live merchant systems. The Phase 2 handoff/design record is `specs/WEBMCP-PHASE-2-READINESS-INTEGRATION.md`.
- The canonical seven-tool descriptor catalog lives in `packages/webmcp`; native and replay execution must invoke those same handlers, with shopper approval coordinated outside the engine.
- RetailAgentOS provides seven canonical Phase 1 WebMCP tools plus an optional post-cart revision extension (`revise_validated_cart`, added after Phase 1 shipped — see `OPTIONAL_CART_REVISION_TOOLS`/`ALL_WEBMCP_TOOLS` in `packages/webmcp/src/index.ts`). It is dynamically registered only after a Fresh Corner cart exists (never before a cart, during approval, for TheCustomHub, or when the SDK's `enableCartRevision` is false), revalidates the full proposed line set through the same gateway/engine path, and cannot check out, place an order, or initiate payment. Do not describe it as part of the original seven-tool Phase 1 catalog.
- Dynamic phase tools are registrations, not disabled UI affordances. Abort registration controllers on reset, scenario switch, and unmount; never duplicate commerce-policy calculation in React or WebMCP.
- Historical provenance matters: native browser WebMCP is shipped for the controlled showcase; the generalized remote/server MCP is designed, not shipped. Keep pre-challenge foundations distinct from challenge-period commits `92753e5`, `d094e12`, `e464bb8` (Aug 30–31, 2026), `d9a5eb5` (judge-facing UX/truthfulness), `0228160` (optional cart-revision extension), `5b1603e` (submission-hardening pass), `12f8ba0` (deterministic native approval-to-cart handoff, which also carries the server-side cart idempotency, dispose/cleanup, and retry-recovery work), `0b0b71a` (WebMCP challenge showcase hardening), `6a57c09` (structured TheCustomHub quote workflow), `4790f74` (focused challenge navigation and page identity), and `b0550a8` (documentation/evidence reconciliation, not a product change) — and update public agent, evidence, developer, and build-log surfaces together when changing this terminology.
- The judge-facing `/webmcp-showcase` UI is split into `src/components/showcase/*` (hero, mission launcher, scenario selector, mission timeline, decision summary, developer evidence) orchestrated by `src/app/agent-ready-storefront/storefront-client.tsx`. Guided replay is always labelled "Guided replay · Same RetailAgentOS handlers · No external agent" and must remain available even when native WebMCP is detected — never gate the guided button on the absence of `document.modelContext`.
- WebMCP telemetry `source` is per-invocation, not inferred from browser capability: `registration.invoke()` (guided) always passes `source: 'replay'`; an omitted `source` means a real browser called the registered descriptor directly (`'native'`). Never reintroduce a shared mutable "current source" flag for invocation events — see `packages/webmcp/src/index.ts`.
- Mission Control (`MissionTimeline.tsx`) groups consecutive raw `registered`/`unregistered` telemetry events from the same registration wave into one business-readable row; this is presentation-only grouping — never drop, mutate, or filter the underlying `events` array itself, since Developer Evidence renders it verbatim.
- The shopper-approval card (`ShopperApprovalCard.tsx`) shows a completed "Approved by shopper" state, not a vanished card, followed by the true chronological sequence — human approval → WebMCP capability registered → `prepare_validated_cart` invocation (native/guided/waiting) → RetailAgentOS validation. Never label a UI click as a WebMCP invocation, and never mark the invocation step done from the approval click itself.
- Once a cart exists, `DecisionSummary.tsx` shows the `CART_PREPARED`/`CART_REVISED` `code`/`nextAction` straight from the `prepare_validated_cart`/`revise_validated_cart` gateway response (never recomputed in React), not the underlying plan decision's stale `ELIGIBLE` copy.
- Farm Eggs' canonical title/unit ("Farm Eggs, dozen" / "1 dozen") is sourced once from `src/lib/showcase/productDisplay.ts` and `fixture.ts`'s `quantityUnits` map — never hardcode a duplicate title/unit string in a React component.
- **Post-approval native handoff is deterministic by construction, not by luck.** `packages/webmcp/src/index.ts`'s `activatePhase()` fully registers and awaits every next-phase tool *before* the triggering tool's `execute()` call returns; only the superseded phase's cleanup (including the currently-executing tool's own registration) is deferred to a following tick, via per-tool generation tokens (`toolGeneration`) so a late cleanup can never remove a same-named tool a newer transition already re-registered. Do not reintroduce a "defer the whole transition" pattern (e.g. a bare `setTimeout(0)` before returning a tool's result) — that reopens the race where a native browser agent can receive `apply_plan_repair`'s result before `prepare_validated_cart` is actually registered. Native and guided (`registration.invoke()`) execution must keep calling the identical descriptor/gateway handlers regardless of this timing.
- `apply_plan_repair`'s successful result carries a top-level continuation contract (`decisionId`, `lines`, `allowedNextActions: ['prepare_validated_cart']`, `nextAction`, `cartCreated`/`checkoutAvailable`/`checkoutStarted`/`orderPlaced: false`) in addition to the preserved nested `decision`/`repair` objects, so a browser agent can act without parsing nested fields.
- Cross-agent recovery is explicit, truthfully labelled, and never automatic: it appears only after `prepare_validated_cart` is genuinely registered, no invocation/cart exists, and ~5s have elapsed, and its "Guided fallback" button is always tagged `source: 'replay'` through the same `registration.invoke()`/canonical-handler path as every other guided call — never described as native WebMCP, and never triggered without an explicit shopper click. It is single-flight guarded so a resuming native agent and a fallback click cannot both prepare a cart.
- **(Shipped — committed on `main` as `12f8ba0`: server-side cart-preparation idempotency.)** `ShowcaseGateway.prepareCart` (`src/lib/showcase/gateway.ts`) is guarded by two independent idempotency layers, not one: the pre-existing caller-supplied-idempotency-key cache is unchanged and stays the first check; a second, trusted server-side layer (`cartsByDecision`) is keyed by `storefrontId + storefrontSessionId + eligible decisionId` and stores a canonical (order-independent) line fingerprint alongside the resulting `CartResponse`. Two callers preparing a cart for the identical decision and lines — a native WebMCP call and a guided-fallback replay, racing with different caller-supplied idempotency keys — always converge on the exact same stored cart reference; a decisionId reused with different lines is rejected with a bounded error (in practice `DECISION_MISMATCH` from the pre-existing per-decision lines check, since `decisionId` already 1:1-encodes its evaluated lines — the new layer's own `CART_PREPARATION_CONFLICT` is a defense-in-depth integrity check on `cartsByDecision` itself, exercised directly in `gateway.test.ts` since the natural collision path is otherwise unreachable). No checkout/order/payment behavior is touched by this layer.
- **(Shipped — committed on `main` as `12f8ba0`.)** `packages/webmcp/src/index.ts`'s `dispose()` always aborts every controller — current phase, base, session, and any still-pending superseded-phase controller (tracked in `pendingCleanups`, keyed by generation) — even when `dispose()` runs strictly before that generation's deferred `setTimeout(0)` cleanup tick has fired. The single teardown function, `performCleanup(generation)`, always aborts the controller unconditionally first; only the telemetry emission and `activeTools`/`toolGeneration` bookkeeping after that abort are suppressed once disposed (dispose already clears that bookkeeping itself). `performCleanup` is also called proactively, synchronously, from `activatePhase()` right before registering a tool name that collides with a still-pending stale generation (e.g. a rapid REPAIRABLE → approved `apply_plan_repair` → ELIGIBLE → immediate re-evaluate back to REPAIRABLE, before the first transition's cleanup tick elapses) — this is what keeps a real host that rejects re-registering an in-use name from ever seeing a duplicate.
- **(Shipped — committed on `main` as `12f8ba0`.)** Guided-fallback cart-preparation failure is recoverable, never silently stuck: `storefront-client.tsx` tracks a `cartPreparationState` (`idle | invoking | failed | prepared`), distinct from mere invocation attribution (`cartInvocationSource`, which fires on the WebMCP `invoked` telemetry event before the outcome is known). A failed/cancelled attempt that produced no cart (WebMCP `failed`/`cancelled` telemetry, or a completed-but-ineligible `onCart` result with `cart: null`) always releases the client single-flight lock and surfaces a truthful, bounded error/retry banner (`ShopperApprovalCard`'s "Cart preparation failed" block, independent of the pre-invocation `recoveryPhase` waiting/timeout banner) — an explicit "Retry guided cart preparation" click is the only way to try again; nothing here ever retries automatically.
- The actor order for the approval-to-cart journey is always: shopper approval → WebMCP capability registration → `prepare_validated_cart` invocation → RetailAgentOS validation. Codex Browser completed this journey natively before the native-handoff-hardening pass; a separate ChatGPT browser-agent run exposed the registration-timing weakness that pass fixed — do not claim the native flow was universally broken. The deployed-origin native walkthrough has since been run: the maintainer completed it in ChatGPT's in-app browser against `https://www.retailagentos.com/webmcp-showcase` on 2026-09-02 (build `5257759`). Attribute that result to the maintainer's report rather than restating it as self-verified, and re-run it after any change to the registration lifecycle, the gateway, or the showcase route instead of relying on the record indefinitely.
- `packages/platform-contracts` builds its ESM/CJS/declaration output from its own `tsconfig.build.json` (`incremental: false`, `composite: false`), not the root Next.js tsconfig — verify with `npm run build -w @retailagentos/platform-contracts` before claiming all standalone packages build.
- `NavBar.tsx`'s desktop nav/CTA and mobile hamburger/drawer switch at the `lg` breakpoint (not `md`), so a ~768px tablet viewport gets the mobile drawer instead of an overflowing desktop row; never make both navigation systems visible at once.
- The canonical `/webmcp-showcase` and compatibility `/agent-ready-storefront` routes use focused challenge chrome: RetailAgentOS identity, challenge badge, Run Demo, How It Works, Developer Evidence, GitHub, and Back to RetailAgentOS. They do not render the normal dropdown-heavy company navigation or large multi-column footer. Other site routes retain the normal platform navigation. Never render both navigation/footer systems on the same route.
- `src/components/layout/AppShell.tsx` is the single place that decision is made (`isShowcaseRoute(pathname)`), swapping `NavBar`/`Footer` for `ShowcaseHeader`/`ShowcaseFooter`. Never add a second showcase page component, a nested showcase layout, or a route-group duplicate — both routes render the one `storefront-client.tsx` instance, and layout changes must never cause WebMCP registration churn. `storefront-client.tsx` returns a plain `<div>`, not a `<main>`: AppShell already provides the page's single `main` landmark.
- AppShell's non-fullscreen wrapper carries `shrink-0`. `body` is a fixed-height (`h-full`) column flex container, so without it the wrapper is shrunk back to one viewport while its content overflows — and that capped wrapper is the sticky challenge header's containing block, which made the header stop sticking about one viewport down the page.
- Showcase naming, links, anchor ids, canonical URL, and the optional video URL are defined once in `src/lib/content/showcaseChrome.ts`; page metadata for both routes comes from `src/lib/content/showcaseMetadata.ts`, so the compatibility route can never present a divergent title/description or a competing canonical URL. Navigation label is "WebMCP Live Demo" (it replaced "WebMCP implementation" in `developerLinks.ts`); page/product label is "RetailAgentOS WebMCP Agent Storefront" — one word, normal capitalization, never "StoreFront", and RetailAgentOS itself is never renamed to "WebMCP Storefront".
- Judge anchors are `#webmcp-mission` (mission launcher, renamed from `mission-launcher` — never duplicated), `#why-webmcp` (business comparison), and `#developer-evidence`. Each target is `tabIndex={-1}`, `aria-labelledby`-named, and carries the `.showcase-anchor` class (`scroll-margin-top`) so the sticky header cannot cover it. Anchor navigation is plain fragment navigation — no timers, no scripted scrolling, and never conflated with WebMCP invocation telemetry. Smooth scrolling is scoped by `:root:has(.showcase-header)` and disabled under `prefers-reduced-motion`; the root layout's `<html data-scroll-behavior="smooth">` is required by Next.js 16 so route transitions still jump instantly.
- The "Watch video" hero action renders only when `getShowcaseVideoUrl()` returns a real absolute `https:` URL from `NEXT_PUBLIC_WEBMCP_VIDEO_URL`. Never render a placeholder, a `#` link, or an unactionable "coming soon"; the badge text may say "Built for the OpenAI WebMCP Challenge" but must never imply endorsement, certification, partnership, or selection by OpenAI, and no OpenAI logo is used.
